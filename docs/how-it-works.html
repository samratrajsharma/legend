How Legend actually works

Not a box diagram — the real mechanics. For each feature: the request path, the data structures it touches, and the algorithm.

Everything rests on one idea: index the repo once into an in-memory RepoIndex, then every feature is a pure read over that object. So the whole system is really "build the index" (six stages, below) plus "views over the index" (the features). We'll do the foundation first, then each feature end-to-end.

Core data model

Four structures carry the whole system. Understand these and every feature reads naturally.

Symbol — one function / method / class

Produced by the parser. The atomic unit of understanding.

id"{rel_path}::{qualname}" — globally unique, e.g. model.py::Detector.predictname / qualnameshort name vs dotted path (predict vs Detector.predict)kindfunction · method · classfile / start_line / end_linewhere it livesdocstring / codethe docstring and the raw source slicecallsbare names this symbol calls (e.g. [save, run])parentenclosing class qualname, if a methodcomplexitycyclomatic complexity (branch count + 1)basesbase-class names, if a class

CodeGraph — the wiring between symbols

A pure-Python directed multigraph. Nodes are files and symbols; edges carry a type.

Edge typeMeaningPowers
containsfile → its symbolsFiles "Defines"
callssymbol → symbol it invokescallers/callees, Impact, dead code
method_ofmethod → its classclass structure
importsfile → file it importshub files, import cycles
inheritsclass → base classinheritance view

graph.callers(id) = predecessors on calls; graph.callees(id) = successors. Two adjacency maps (_in, _out) make both O(1).

Chunk — one retrievable piece

Search operates on chunks, not raw files. Each symbol becomes a chunk; each file gets a "module" header chunk; docs get a chunk.

idhash, unique per build (the Chroma / BM25 primary key)textwhat gets embedded & searched: "file :: qualname [kind]\ndocstring\nbody"node_id / symbol_idlink back to the graph node — this is how a search hit expands through the graph

RepoIndex — the in-memory hub

The object build_index() returns and the backend keeps in its _REPOS registry. Every endpoint starts by fetching it.

RepoIndex:
  meta            # name, path, commit, is_git
  parsed_files    # list[ParsedFile] -> each has .symbols
  graph           # CodeGraph
  chunks          # list[Chunk]
  lexical         # BM25Retriever (always built)
  dense           # ChromaRetriever or None (semantic, optional)
  config          # model, data_dir, top_k ...
  memo            # {} cache for pure analyses (insights, overview...)
  chunks_by_node  # node_id -> [chunks]   (graph expansion uses this)
Why it matters: the index is immutable after build, so pure analyses (insights, overview, language breakdown) are memoised on memo — computed once, reused for every later request. A reconnect/recapture builds a new object with a fresh cache, so there is never a stale read.

build 1Ingest & clone

ingest(source, data_dir) turns a git URL or a local path into files on disk.

Is it a URL or a path?

is_git_source() routes URLs to the clone path and everything else to a local-directory read. URLs are then hardened before git ever sees them:

  • Transport allowlist — validate_git_url() permits only http/https/ssh/git. It rejects ext:: (which would run a shell command as the "transport" — a remote-code-execution vector) and file://, and any URL starting with - (argument injection). The clone command also uses a -- separator and sets GIT_ALLOW_PROTOCOL as defence in depth.
  • Normalisation — github.com/o/r, a trailing slash, /tree/main, /blob/main/x.py, ?tab=… all canonicalise to https://github.com/o/r.git.

Reusing vs re-cloning a cached folder

_probe(dest, url) classifies an existing folder so a cached clone is trusted but a corrupt one is not:

StateMeaningAction
okreal repo, right originreuse (fetch latest)
errorreal repo but git erroredreuse anyway — deleting working code to chase a git hiccup is wrong
mismatchdifferent repo, same folder nameclone into a url-keyed folder
brokenno .git — half-clonedelete & re-clone

Clone falls back progressively: --depth 200 → --depth 1 → full, with one retry each. On Windows, cleanup first clears read-only attributes on .git/objects (git marks them read-only, which otherwise makes deletion fail halfway and strand a corpse).

build 2Parsing

parse_file() dispatches by extension.

Python — stdlib ast

The source is parsed to an AST. For each top-level function/class (and each method inside a class), a Symbol is built. Two things are computed in a single tree walk per function:

  • calls — every Call node's callee name. obj.save() reduces to save; resolution happens later in the graph.
  • complexity — start at 1, +1 for each if/for/while/except/and/or/comprehension. Cyclomatic complexity.

Crucially, the walker descends into compound statements — a def hidden inside try/except (the classic import-fallback) or an if TYPE_CHECKING: guard is indexed, where naive "top-level only" parsing would miss it. Closures inside functions stay unindexed (they're local).

JS / TS — regex, and honestly labelled

A best-effort regex pass finds classes, functions, and arrow functions. Line ranges are approximate and complexity is not computed — so JS metrics are intentionally shallow, not silently wrong.

Everything else

Markdown and config files are kept as text (no symbols) so they can be embedded for search and rendered (README) — this is why the README viewer has content to show.

build 3Code graph

build_graph(parsed_files) creates the nodes, then resolves each symbol's bare call names into real edges. Resolution is the subtle part — done naively it manufactures phantom edges.

The resolution ladder

For a callee name like save, candidates = every symbol named save in the repo. Then:

1. exactly one candidate repo-wide      -> link to it        (unambiguous)
2. else, a candidate in the SAME file    -> link to that      (local scope wins)
3. else, one candidate whose module the caller imports -> link (import-scoped)
4. else                                   -> UNRESOLVED, no edge
Why step 4 matters: the old code linked a bare self.save() to every save in the repo, so callers/callees, Impact, dead-code and "used by" were all over-connected and untrustworthy on any real codebase. A missing edge is far better than a wrong one — so an ambiguous name is left unresolved rather than fanned out to all matches.

build 4Chunking

make_chunks() emits, per file: a module header chunk (path + imports + the names it defines), one symbol chunk per symbol (header + docstring + truncated body), and a doc chunk for markdown/config. Every chunk id is made unique within the build — two same-named top-level defs (a redefinition, or a try/except fallback) would otherwise collide and make the vector store reject the whole batch, failing indexing for that repo.

build 5Retrievers

BM25 (lexical) — always built, pure stdlib

Tokenisation is code-aware: it splits camelCase and snake_case into parts and light-stems them, so a query for "authentication" matches AuthService. Scoring is textbook BM25:

score(q,d) = Σ  idf(t) · f·(k1+1) / ( f + k1·(1 - b + b·|d|/avgdl) )
             t∈q
k1 = 1.5   b = 0.75   idf(t) = log(1 + (N - n_t + 0.5)/(n_t + 0.5))

where f = term frequency in the chunk, |d| = chunk length, avgdl = average, n_t = chunks containing the term. Longer chunks are penalised (the b term); rarer terms weigh more (idf).

Chroma (semantic) — optional

If chromadb is installed, each chunk's text is embedded with its on-device MiniLM model (no API key, nothing leaves the machine) and stored in a persistent collection keyed by the index signature. If it is absent, the system runs BM25-only — degraded, not broken.

build 6Caching

Parsing + graph + chunking are pickled to .cache/*.pkl, keyed by a signature. The signature is commit SHA + a fingerprint of every working-tree file's mtime & size. Hashing the working tree (not just the commit) is what lets Timeline notice uncommitted edits on a git repo — with a commit-only key, an edit you hadn't committed reused the stale parse and Timeline reported "no change". The Chroma collection persists separately under the same signature.

Ask — retrieval-augmented Q&A

The flagship. A plain-English question becomes a grounded, streamed answer with cited sources. Full path:

question→POST /ask/stream→hybrid_search→graph expand→assemble_context→litellm (SSE)→answer + sources

1 · Hybrid retrieval

The question runs through both retrievers, each returning a ranked list. The two lists are fused with Reciprocal Rank Fusion — rank-based, so BM25 scores and cosine distances never have to be reconciled on the same scale:

RRF: score(chunk) = Σ  1 / (60 + rank + 1)
                  lists
# a chunk ranked #1 by BM25 and #3 by semantic scores 1/61 + 1/64.
# a chunk found by both lists is a "both" source -> shown to the user.

2 · Graph expansion

Pure text search misses code that is related but not lexically similar. So the top hits are expanded through the graph: for each, its calls neighbours (both directions), the file that contains it, and its imports are pulled in. A neighbour already in the results gets a small score boost; a new neighbour enters at 30% of the top score, tagged via: graph.

Concretely: ask "how are refunds recorded?" and the retriever finds refund() lexically, then graph-expansion pulls in post_entry() — the ledger function it calls — even though your question never said "ledger". That is the difference between search and understanding.

3 · Context assembly

assemble_context() packs the top blocks into a budget (8 blocks, ~6000 chars), each prefixed with a provenance header [file:start-end :: name]. If the single top chunk alone exceeds the budget it is truncated to fit rather than dropped — otherwise Ask would answer with no context on exactly the big function you asked about.

4 · Generation & streaming

The context + question go to synthesize_stream(), which calls litellm.completion(stream=True). Tokens are forwarded as they arrive over Server-Sent Events: the backend emits sources first, then a run of token events, then done. The React page reads the fetch body as a stream and appends tokens live, so the answer types out. No model configured? The endpoint returns a clean needs_llm event instead of erroring — retrieval still ran, so the sources are shown regardless.

Overview

A single call, insights.repo_insights(idx), walks the graph once and derives:

  • Hub files — highest import degree (fan-in + fan-out). Central files where a change ripples widely.
  • Entry points — files that look like starts (main, app/CLI entry, servers).
  • Most complex symbols — top cyclomatic complexity.
  • Likely unused — symbols with zero calls predecessors, excluding classes, dunder methods, and entry files.
  • Totals — LOC, symbol count, average complexity.

Alongside it, language_breakdown() aggregates files/LOC/symbols per language and config_surface() regex-scans yaml/toml/ini/json/CLI-args for the configuration knobs (it reads indented keys too, so nested ML configs aren't missed). The whole response is memoised on idx.memo.

Files & README

The tree is the parsed-file list. Selecting a file fetches its content and its per-file summary (insights.file_summary: purpose from the module docstring, complexity total, fan-in/out, and the symbols it defines as clickable chips). Clicking a chip triggers the function explainer (below). A .md file renders through the same markdown component as Overview — headings, lists, tables, code — instead of raw text.

Function explainer

GET /functions/explain finds the symbol, gathers its code plus its callers and callees from the graph, and (if a model is set) asks for a structured explanation: what it does / parameters / returns / how it works / edge cases. With no model it still returns the code and the caller/callee lists — useful on its own.

Insight Graph

The interactive architecture map (formerly "Diagrams"). A separate stdlib tool, codemap, walks the repo and groups files into areas (by directory / dependency band), then lays them out into bands with dependency edges between them. The backend runs it once and caches the result; the React page renders it as pannable/zoomable SVG with node fills neutral and green reserved for hover and selection, so the structure reads without colour noise. Clicking an area drills into its files and symbols.

API & DB

Two regex passes over the source. api_map() finds HTTP route decorators/calls — @app.get(...), @router.post(...), app.route(...), Express-style — and records method + path + file. db_map() finds ORM models (classes whose base is a known DB base) and __tablename__ declarations. The tab shows 10 rows with a "show all" toggle so a large surface stays readable.

Timeline & Track — the differentiator

These answer "what changed over time", the feature no plain search tool has. Two mechanisms.

Structural fingerprint & diff

A capture re-indexes the folder and records a compact structural fingerprint — per file: its symbols with kind and complexity, LOC, totals — into an append-only events.jsonl. The next capture diffs the new fingerprint against the last and records exactly what moved:

Files
added / removed / modified
Symbols
added / removed / changed
Complexity
per-symbol from→to deltas

It is entirely LLM-free — pure structural comparison. A cheap folder-signature "dirty" check (mtime+size) lets auto-capture fire only when something actually changed. Optional narration can turn a diff into prose, but the tracking itself needs no model.

Git history import

Timeline also backfills from git commits. Two subtleties, both fixed the hard way:

  • Merges show their files. Plain git log --name-status prints nothing for a merge, so ~40% of commits had blank details. Using --diff-merges=separate lists what a merge changed against each parent — but that emits one entry per parent, so the parser dedups by SHA and unions the files, giving one timeline row per commit that is never blank.
  • Existing timelines re-enrich. Commit events are a projection of git, so import rebuilds them from git (the source of truth) rather than append-and-dedup — improvements reach timelines imported by older versions, while captures (which aren't in git) are preserved.

Track (commit diff)

Track is the on-demand version: pick two commits, and it snapshots the repo at each (via git worktree), re-indexes both, and shows the structural diff — files, symbols, complexity changes, and the architecture delta. The heavy part is indexing two commits, so the first diff on a large repo takes a moment.

The Intel tabs surface errors instead of hanging: if an analysis fails, you get the reason, not an eternal spinner.

Report export

The Download report button (top bar, every tab) assembles one structured report and renders it in three formats. _report_sections(idx) gathers Overview, languages, entry/hub files, complexity, routes, models, config surface, tech-debt summary, dead code, and the file list into a format-agnostic list of sections. Three renderers consume that same structure:

.md
pure Python string assembly — zero dependencies, always works
.docx
python-docx — headings, styled tables
.pdf
reportlab platypus — flowables, wrapped table cells

The doc libraries are imported lazily, so if they're missing only the report feature returns a clear error — the backend still starts and every other feature works.

LLM provider layer

Bring your own model. providers.py is a small registry — each provider is one entry of {label, key_env, prefix, base_url, models}. resolve(provider, model, base_url) returns the litellm model string (e.g. gemini/gemini-2.0-flash) plus any extra kwargs, and litellm handles the actual API dialects. Adding a provider is a one-line registry entry, and the Settings UI is generated from the registry.

Supported: OpenAI, Anthropic, Google Gemini (native), Groq, OpenRouter, local Ollama, and a custom base-url option. Every LLM-touching feature degrades gracefully to a "connect a model" state when no key is set, so the tool is fully usable for indexing, search, structure and tracking with no model at all.

Local-first & security

The design guarantee: your code never leaves your machine except where you explicitly reach out.

  • Only two egresses: the git clone on connect, and LLM calls for Ask/explanations. Indexing, embeddings (on-device MiniLM), search, graph, timeline and reports are all local.
  • Loopback only: the backend binds 127.0.0.1; the browser talks to it through the Vite proxy.
  • Clone hardening: transport allowlist blocks the ext:: RCE and file:// reads; -- separator blocks argument injection.
  • Path-guarded file reads: file content is served from the parsed set, not by arbitrary path traversal.
  • XSS-safe UI: all repo/LLM/README content renders as React text — no dangerouslySetInnerHTML — so a malicious README can't inject script.

This document reflects the current codebase after the correctness, security and performance passes: scoped graph resolution, working-tree cache signatures, iterative cycle detection, transport-allowlisted cloning, memoised analyses, and merge-aware git history.
